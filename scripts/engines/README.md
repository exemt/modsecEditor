# Стенд: линтер против настоящих движков

Всё, что `src/seclang` утверждает о движках, взято из их исходников. Стенд проверяет, что
прочитано верно: отдаёт одни и те же правила ModSecurity 2, ModSecurity 3 и Coraza и
сравнивает их ответ с тем, что сказал линтер.

Нужны Docker и Node 22.15+.

```bash
node scripts/engines/run.mjs all --write   # всё и запись вердиктов; минут пять
node scripts/engines/run.mjs load          # только загрузка блоков
node scripts/engines/run.mjs names         # только имена каталога
node scripts/engines/run.mjs behaviour     # только сценарии с запросом
node scripts/engines/run.mjs probe папка   # спросить движки о своих *.conf
```

Ключ `--work папка` задаёт рабочую папку (по умолчанию — во временной папке системы); в ней
же остаются подробные отчёты `load.json`, `names.json`, `behaviour.json`, `probe.json` и
кэш модулей Go, чтобы Coraza не скачивалась заново.

## Движки

| Движок | Образ | Как запускается |
| --- | --- | --- |
| ModSecurity 2 | `owasp/modsecurity-crs:apache` | `httpd -t` с `apache/httpd.conf` и правилами через `-c "Include …"` |
| ModSecurity 3 | `owasp/modsecurity-crs:nginx` | `nginx -t` с `nginx/nginx.conf`, правила — в `modsecurity_rules_file` |
| Coraza | `golang:1.25-alpine` | загрузчик `coraza/main.go` на библиотеке `corazawaf/coraza/v3` |

Версии, с которыми вердикты записаны, названы в начале `src/seclang/stand/verdicts.json`.
Обновили образ — перезапустите стенд с `--write` и посмотрите, что изменилось в файле:
расхождение с прежними вердиктами — это и есть разница между версиями движка.

## Что проверяется

**Имена.** Для каждого имени каталога — переменной, оператора, преобразования, действия,
директивы — пишется самое малое правило с ним и грузится в каждый движок. Ответ сверяется с
таблицами `src/seclang/engines.ts`.

**Загрузка.** Каждый блок из `src/seclang/cases/*.conf` и каждая проба из
`src/seclang/stand/probes.conf` грузится отдельным файлом. Линтер с настройкой `engine`
обязан назвать ошибкой то, что этот движок не загрузил. Блоки нарочно малы: один вопрос на
блок, чтобы отказ нельзя было списать на что-то ещё.

**Поведение.** `scenarios.json` — правила, запрос и ожидаемый исход в каждом движке:
`pass` — запрос дошёл до сервера, `402`/`403` — остановлен правилом с этим кодом, `ERR` —
правила не загрузились. У ModSecurity запрос настоящий, через `curl`; у Coraza запрос
проводится через те же фазы вызовами библиотеки. Ожидание записано словами утверждения
линтера (`claim`), так что сценарий — это проверяемая формулировка: «макрос в `skipAfter` не
раскрывается», «`@streq` не заполняет `TX.0`».

## Как добавить вопрос к движкам

- «Грузит ли движок такую запись?» — блок в `src/seclang/stand/probes.conf`:
  строка `# probe: имя` и правила под ней.
- «Как движок себя ведёт на запросе?» — запись в `scenarios.json`.

Потом `run.mjs all --write` и `npx jest src/seclang/stand`. Если линтер с движком не
согласен, тест назовёт блок; дальше либо правится линтер, либо расхождение вписывается в
список оговорок в `src/seclang/stand.test.ts` — с причиной.

## Что стенд уже показал

Линтер до сверки ошибался, и не в мелочах. Исправлено по вердиктам:

- таблицы совместимости: `t:uppercase` нет в ModSecurity 2; `USERAGENT_IP` и
  `SecRequestBodyInMemoryLimit` нет в третьей версии; `IP` и `exec` неприменимы в Coraza;
- порядок исключений: в третьей версии директива-исключение действует и тогда, когда стоит
  выше правила, — линтер считал это промахом для всех;
- макрос в шаблоне `@rx` Coraza не раскрывает — линтер считал, что раскрывают все;
- звено цепочки без списка действий третья версия грузит только перед пустой строкой;
- два слэша подряд в шаблоне значат разное: Apache отдаёт второй версии один;
- запись, которую грузит только вторая версия: список действий без кавычек, одинарные
  кавычки вокруг аргументов, запятая в конце списка, значение с пробелом без кавычек;
- запись, которую не грузит только Coraza: области проверки в кавычках, имя оператора не в
  том регистре, запись в коллекцию кроме `TX`, преобразование в `SecDefaultAction`.

И подтверждено то, что было прочитано верно: выборка по тегу — шаблон у второй версии и
строка у остальных; `%{VAR:key}` раскрывает только третья; макрос в `skipAfter` не
раскрывает никто; `setvar` в голове цепочки исполняется, даже когда цепочка не совпала;
`@streq` с `capture` ничего не захватывает; слэши в одинарных кавычках считаются после
свёртки.

А про захват стенд показал, что линтер держал в голове не ту модель. Он считал, что группа
живёт внутри правила; на деле `TX.0`…`TX.9` доживают до конца запроса, `capture` действует
только на оператор своего условия, а `setvar` головы цепочки исполняется раньше, чем звено
успеет что-то захватить. Сценарии `capture-…` — это та модель, на которой теперь стоят
замечания о захвате; расходятся движки в двух местах — `capture` в `SecDefaultAction`
третья версия не исполняет, а старшие группы после нового захвата стирает только вторая.

Сценарии `anchors-…` проверяют якоря. `^` и `$` во второй версии — края значения, в
третьей и Coraza — ещё и границы строк; точку все три собирают так, что она берёт перевод
строки. Заодно выяснилось, где перевод строки вообще бывает: `ARGS` раскодированы везде,
`REQUEST_URI` — только в третьей версии, а `QUERY_STRING`, `REQUEST_LINE`,
`REQUEST_URI_RAW` и куки движки отдают как есть. Совет заменить `@rx ^admin$` на
`@streq admin` раньше давался всем подряд; теперь он стоит на этих вердиктах.

Сценарии `decode-…` разбирают раскодирование целиком: переменная, фаза, движок. Самое
неожиданное — вторая версия: путь она берёт у Apache, а тот раскодирует его только после
первой фазы, так что `REQUEST_FILENAME` в первой фазе ещё `/p%41th`, а во второй уже
`/pAth`. Третья версия раскодирует `REQUEST_URI` весь, Coraza — только путь
(`REQUEST_FILENAME`). Отсюда замечание `validateDecodedInput` и находка в CRS 3.3.10:
правило 920220 проверяет кодирование в уже раскодированном `REQUEST_URI` и на верном `%25`
срабатывает под обеими версиями ModSecurity.

Последний заход — нюансы, которые линтер не видел. Регистр: в списке областей правила имя
параметра регистр не различает никто, а в исключении третья версия сравнивает его буква в
букву — и для заголовков тоже, хотя по HTTP/2 они приходят строчными. Шаблон по именам
параметров регистр различает одна Coraza; по `TX`, куки и заголовкам она переводит шаблон в
нижний регистр сама. Цепочки: `SecRuleUpdateTargetById` убирает область из звена только во
второй версии, `ctl:ruleRemoveTargetById` — только в Coraza. Байты: ModSecurity собирает
шаблон без UTF-8, и `[é]` для него два байта порознь. И три сценария повторяют CRS
(`anchors-negated-in-chain`, `anchors-header-after-decode`, `anchors-exclusion-trigger`):
в третьей версии и Coraza валидатор и исключение с `^…$` обходятся лишней строкой.
