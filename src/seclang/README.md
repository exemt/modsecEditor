# seclang — разбор и проверка правил ModSecurity

Самодостаточный модуль: ничего не импортирует снаружи своей папки, не знает ни о редакторе,
ни о браузере (проверяется `independence.test.ts` и отдельным `tsconfig.json` без DOM).
Вынести его в отдельный пакет — значит перенести папку.

Три слоя, каждый стоит на предыдущем и ничего в нём не меняет:

| Слой | Вход → выход | Файл |
| --- | --- | --- |
| `parse` | текст → синтаксическое дерево | `parser.ts`, `ast.ts` |
| `analyze` | дерево → смысл: цепочки, конвейер с типами, указатели | `analyze.ts` |
| `lint` | дерево + смысл → замечания | `lint/` |

Знание о языке лежит отдельно: `catalog.ts` — какие бывают имена и что они значат,
`value.ts` — типы значений, `engines.ts` — что из языка понимает каждый движок,
`regex.ts` — перевод шаблонов PCRE.

```ts
import { parse, analyze, lint } from './seclang';

const file = parse(source);     // FileNode
const model = analyze(file);    // Model
const problems = lint(source);  // Diagnostic[]

// Набор файлов в порядке загрузки: метки, номера и умолчания видны между файлами.
const perFile = lintWorkspace([{ name: 'setup.conf', source: a }, { name: 'rules.conf', source: b }]);
```

## Дерево

У каждого узла есть `kind` и границы в исходнике: `start` включён, `end` исключён, оба —
смещения в символах. Границы точные и там, где запись разорвана переносом `\` или содержит
`\"`: значение узла уже разобрано, границы — всегда про исходник.

```
File
├─ Comment
├─ Directive ─ Argument*
├─ SecMarker ─ Argument
├─ SecAction / SecDefaultAction ─ ActionList
├─ SecRuleScript ─ Argument, ActionList
└─ SecRule
   ├─ VariableList ─ Variable* ─ Selector?
   ├─ Operator ─ Text ─ Macro*
   └─ ActionList ─ (Action | Transform | Setvar | Ctl)* ─ Text? ─ Macro*
```

`forEachChild`, `walk` — обход; `nodePathAt(file, offset)` — путь от корня к узлу под
курсором; `statementAt` — утверждение под смещением; `LineIndex` — смещение ↔ строка и столбец.

Чего не хватает, то остаётся `null` (`SecRule ARGS` — правило без оператора), а что не
читается однозначно — попадает в `file.issues`. Исключений парсер не бросает ни на каком входе.

## Типы по конвейеру

Правило — труба: области проверки отдают значение, преобразования его меняют, оператор
сравнивает. Про значение на каждом шаге известны **вид** (`string`, `number`, `binary`,
`any`) и **свойства** — что о нём верно наверняка (`Lower`, `NoSpace`, `Hex`, `Digest`,
`OneLine`, …). Свойства бывают и у самих переменных: в методе, заголовках, куки и
`QUERY_STRING` перевода строки нет (`OneLine`) — перевод строки разделяет поля HTTP, а
движки их не раскодируют.

```
SecRule ARGS:password "@streq 5F4D…" "id:100,phase:2,deny,t:md5,t:hexEncode,t:lowercase"

t:md5        ok     string              → binary<Digest>
t:hexEncode  ok     binary<Digest>      → string<Lower,NoSpace,…,Hex>
t:lowercase  idle   string<Lower,…,Hex> → то же самое
```

Отсюда и ответы, ради которых всё затевалось:

- **годится ли шаг к тому, что отдал предыдущий** — `PipelineStep.status`: `ok`, `idle`
  (ничего не изменит), `mismatch` (вход не того вида), `reset` (`t:none`), `unknown`;
- **можно ли поставить преобразование в это место** — `stepStatus(transformSpec(name), type)`,
  где `type` — выход предыдущего шага;
- **что получит оператор** — `condition.pipeline.output`.

Проверки поэтому не перебирают известные пары имён. `t:trim` после `t:removeWhitespace`
лишний не потому, что эта пара где-то записана, а потому, что во входе шага уже нет пробелов;
`@streq ABCDEF` после `t:hexEncode` не совпадёт по той же причине, что и после `t:lowercase`.

Преобразования из `SecDefaultAction` той же фазы входят в конвейер первыми и помечены
`inherited`.

Вид известен не всегда, и это не недоделка, а честный ответ. Что лежит в `TX:score` или в
`REQUEST_HEADERS:Content-Length`, решает автор правил или приложение, а не движок, — у таких
областей вид `any`, и о типах проверки молчат. Свойства при этом копятся как обычно:
`@streq POST` после `t:lowercase` не совпадёт, чем бы ни было значение.

## Набор файлов

`analyzeAll(files)` и `lintWorkspace(files)` принимают файлы в порядке загрузки. Сквозь
границы файлов видно то же, что видит движок: метка для `skipAfter` ищется во всём наборе,
номер правила занят один раз на всю конфигурацию, `SecDefaultAction` действует и на файлы,
идущие следом. Одиночный файл — набор из одного.

Если набор живёт долго, а меняется в нём один файл за раз, — это редактор, — разбирать всё
заново незачем. `createWorkspace()` хранит разбор по файлам и повторяет его только там, где
изменился текст; модель набора строится заново, потому что правка одного файла меняет
сказанное о других:

```ts
const workspace = createWorkspace({ engine: 'coraza' });
workspace.set('crs-setup.conf', setup);
workspace.set('rules/REQUEST-942.conf', rules);
workspace.lint();                        // замечания по файлам, в порядке загрузки
workspace.set('rules/REQUEST-942.conf', edited); // заново разбирается только он
```

## Указатели: метки, переменные, коллекции

У правила есть связи, смысл которых лежит не в нём самом. `symbols.ts` собирает по всему
набору, где каждое имя объявлено и где использовано; лежит это в `model.scope`.

| Что | Объявление | Использование | Замечания |
| --- | --- | --- | --- |
| Метка | `SecMarker END` | `skipAfter:END` | нет вовсе (`missingMarker`), стоит выше перехода (`markerBehind`), объявлена дважды (`duplicateMarker`), никто не прыгает (`unusedMarker`) |
| Переменная | `setvar:tx.score=+5` | `TX:score`, `%{tx.score}`, `expirevar` | никто не выставляет (`txNeverSet`, `variableNeverSet`), выставляют позже чтения (`txReadBeforeSet`) |
| Захваченная группа | `capture` рядом с оператором | `%{TX.1}`, `TX:0` | забыт `capture` (`captureMissing`), выше никто не захватывает (`groupNeverCaptured`), в журнал идёт чужая группа (`groupFromEarlierRule`), захват никто не читает (`captureUnused`), захватывать нечем (`captureWithoutRegex`) |
| Коллекция | `initcol:ip=…`, `setsid`, `setuid` | `IP:hits`, `setvar:ip.hits=+1` | к ней обращаются, а открыть забыли (`collectionNotInitialised`) |
| Счёт правил | — | `skip:N` | правил в фазе осталось меньше (`skipBeyondEnd`) |
| Правило | `id:942100`, `tag:…`, `msg:…` | `SecRuleRemoveById`, `SecRuleUpdateTargetByTag`, `ctl:ruleRemoveTargetById=…` | исключение ни до чего не дотянулось — см. ниже |

Захваченная группа — указатель особого рода: объявляет её не имя, а `capture`, и живёт она
не в правиле, а до конца запроса. В главном три движка согласны, и проверено это на них самих:

- `capture` действует на оператор того условия, в чьём списке действий записан. В голове
  цепочки он не заставит захватывать звено, в звене — голову;
- правило без `capture` групп не трогает, правило с `capture`, которое не совпало, — тоже.
  `%{TX.1}` без своего `capture` поэтому не пусто, а равно тому, что захватило правило выше;
- `setvar` головы исполняется, когда совпала голова, — раньше, чем звено успеет что-то
  захватить; `msg` и `logdata` раскрываются, когда совпала вся цепочка.

Отсюда и замечания. Чтение, которое само правило не заполняет, — либо забытый `capture`
(оператор группу нашёл бы, но сохранить её нечем: `captureMissing`), либо расчёт на правило
выше. Второе — обычный приём, пока группу читают областью проверки или аргументом оператора:
«захватил в одном правиле, проверил в другом». Линтер проверяет только, что захватывающее
правило и правда исполняется раньше — по фазе и порядку, как у переменных
(`groupNeverCaptured`). А в `msg`, `logdata` и `setvar` чужая группа выдаёт себя за находку
самого правила, и об этом сказано советом (`groupFromEarlierRule`). Сколько групп в шаблоне,
тоже считается: `%{TX.2}` при одной скобке не заполнит никто.

Исключения — тоже указатели, и порядок у двух их родов противоположный. Директива
применяется, пока конфигурация читается, и обязана стоять **ниже** правила
(`exclusionBeforeRule`, между файлами — `exclusionInEarlierFile`). `ctl` применяется, когда
сработал его носитель, и обязан отработать **раньше** цели (`exclusionCtlAfterRule`).
Остальное — запись (`exclusionBadId`, `exclusionCtlTargetList`…), правило, которого нет
(`exclusionNoMatch`), и правило, которое уже снято (`exclusionRemovedThenUpdated`).

О промахе линтер говорит, только когда видно, что набор загружен: надстройка над чужими
правилами, где `SecRuleRemoveById 942100` ссылается на файл, которого здесь нет, — обычное
дело, а не ошибка.

Выборку по тегу и по сообщению движки читают по-разному, и это не про имена, а про
поведение: ModSecurity 2 собирает из неё регулярное выражение и ищет его в теге,
ModSecurity 3 и Coraza сравнивают строки целиком. `SecRuleRemoveByTag "^attack-"` у вторых
не снимет ничего — молча. Без настройки `engine` о такой записи говорит
`exclusionPatternNotPortable`.

Порядок исполнения — не порядок файла: движок проходит фазу целиком и только внутри неё
идёт по строкам. `setvar` из пятой фазы, написанный в начале файла, случится позже чтения
во второй. Поэтому «раньше» считается по фазе и только потом по месту в наборе
(`runsBefore`), а в долгоживущих коллекциях не считается вовсе: значение там могло остаться
от прошлого запроса.

Чего проверки сознательно не трогают:

- `&TX:limit` — проверка наличия, а не чтение. Правило, которое так убедилось, что
  переменная есть, читает её без замечаний: это и есть защита от пустого значения;
- `setvar:tx.%{rule.id}_hit=1` — имя известно только на запросе, но не любое: чтение
  `tx.942100_hit` такой записью объяснить можно, а `tx.score` — нет;
- метку или переменную из макроса, служебные поля коллекций (`IS_NEW`, `UPDATE_COUNTER`)
  и переменные, которые выставляет сам движок.

## Регулярные выражения

Движок считает шаблоны через PCRE, а в браузере есть только `RegExp`. Поэтому шаблон
сначала переводится (`regex.ts`): встроенные флаги `(?i)`, сверхжадные кванторы, атомарные
группы, POSIX-классы, `\A`/`\z`, `\h`/`\R`, `\Q…\E`, `\x{ff}` — и только потом
компилируется. Не собрался — `invalidRegex`; то же для шаблона в параметре области
проверки (`ARGS:/^id_/` → `invalidSelectorPattern`). Если в шаблоне есть запись, которую
перевести нечем (рекурсия, `\K`), проверка молчит: сказать «некорректно» про рабочее
правило хуже, чем промолчать.

Остальное — приметы шаблона, написанного не так, как задумано: подходит ко всему
(`matchesEverything`, `negationMatchesNothing`), может уйти в перебор (`possibleRedos`),
оказался обычной подстрокой (`regexIsPlainText`, `anchoredLiteralRegex`), точка вместо
`\.` (`unescapedDot`), лишнее `.*` в начале, захватывающая группа без `capture` (если
на неё не ссылается сам шаблон: `(['"])…\1`).

Якоря `^` и `$` движки понимают по-разному, и проверено это на них самих (сценарии
`anchors-…` стенда). ModSecurity 2 собирает `@rx` так, что это края всего значения.
ModSecurity 3 и Coraza — в многострочном режиме: `^admin$` у них подойдёт и к `x\nadmin`,
и к `admin\n`. Поэтому `@rx ^admin$` — это `@streq admin` (`anchoredLiteralRegex`, с
правкой) только во второй версии или там, где переводу строки взяться неоткуда: метод,
заголовок, число, значение после `t:compressWhitespace`. В остальных случаях линтер говорит,
что шаблон найдёт слово на любой строке (`anchoredLiteralLines`), и правки не предлагает:
`@streq` проверял бы уже не то же самое. Точку все три движка собирают так, что она берёт
и перевод строки, — потому `^.*admin` равно `admin`, и правка ведущего `.*` убирает якорь
вместе с ним. А `.*+` не трогает: без возврата оно забирает всё значение, и шаблон после
него не совпадёт ни с чем.

`RegExp` принимает и то, что PCRE отвергает: просмотр назад с повтором без границы
(`(?<=a+)b`). Такое ловится отдельно — `lookbehindNotFixed`.

Перевод шаблонов — та же логика, что раньше жила в редакторе: `src/modsec/regex.ts` теперь
только переадресует сюда.

## Движки

Язык один, движков три, и совпадают они не полностью. Каталог знает объединение; разница
лежит в `engines.ts` и включается настройкой `engine`:

```ts
lint(source, { engine: 'modsecurity3' }); // или 'modsecurity2', 'coraza'
```

Без неё правило, верное хоть для одного движка, считается верным. С ней линтер говорит о
действиях, операторах, переменных и директивах, которых в этом движке нет (`notInEngine`),
а для Coraza — ещё и о записях в шаблонах, которых нет в регулярных выражениях Go: просмотры,
обратные ссылки, запрет возврата, `\K`, `\Z`, `\h`, `(?#…)`, флаг `x`, повтор больше тысячи
раз (`regexNotInEngine`).

Различаются движки не только набором имён, но и тем, как читают одну и ту же запись.

Отдельно — что движок раскодирует из URL-кодирования (`%41` → `A`) сам, ещё до
преобразований. Справочники об этом молчат, а движки расходятся; таблица снята со стенда
(сценарии `decode-…`) и лежит в `engines.ts` (`urlDecodedBy`):

| Переменная | ModSecurity 2 | ModSecurity 3 | Coraza |
| --- | --- | --- | --- |
| `ARGS`, `ARGS_NAMES`, `ARGS_GET…`, `ARGS_POST…` | раскодирует | раскодирует | раскодирует |
| `REQUEST_FILENAME`, `REQUEST_BASENAME` | в первой фазе нет, со второй — да | раскодирует | раскодирует |
| `REQUEST_URI` | путь — со второй фазы, параметры — нет | раскодирует весь | нет |
| `REQUEST_URI_RAW`, `QUERY_STRING`, `REQUEST_LINE`, `REQUEST_BODY`, куки, заголовки | нет | нет | нет |

Вторая версия берёт путь у Apache, а Apache раскодирует его между первой фазой и второй:
правило первой фазы видит `/p%41th`, правило второй — `/pAth`. Раскодируют все один раз
(`%2541` приходит как `%41`); `+` в параметрах становится пробелом у всех, а в
`REQUEST_URI` третьей версии остаётся `+`; неправильное `%zz` и `%u0041` остаются как были.

Из этого линтер берёт две вещи. Перевода строки нет в том, что не раскодировано (свойство
`OneLine`, см. «Регулярные выражения»). И `@validateUrlEncoding` на раскодированном значении
ошибается: верное `%25zz` становится `%zz` и проверку не проходит (`validateDecodedInput`).
Справочник второй версии об этом предупреждал — для параметров; что то же случится с
`REQUEST_URI`, видно только на стенде.

От этого зависит уровень замечания. У кода есть список `refusedBy` — какие движки такую
запись не загружают; он виден и в самом замечании. Назван движок из списка — замечание
становится ошибкой. Не назван никакой — становится ею, если отказываются хотя бы два из
трёх: один несогласный движок — различие, а не ошибка. Уровень, назначенный настройкой
`codes` или `topics`, сильнее.

```ts
lint('SecRule &REQUEST_METHOD "@eq 1" "id:1,phase:1,pass"');
// countOnScalar, warning, refusedBy: ['modsecurity2']
lint(sameRule, { engine: 'modsecurity2' }); // countOnScalar, error
```

Таблицы имён (`engines.ts`) собраны по исходникам и справочнику, а проверены стендом: каждое
имя каталога — 323 переменных, оператора, преобразования, действия и директивы —
загружалось в каждый движок. Сверх того их проверяет корпус: рекомендованная конфигурация
движка обязана проходить для него без замечаний, а CRS 4 — для всех трёх.

## Линтер

Проверка — набор обработчиков; движок обходит дерево один раз и зовёт всех подписанных:

```ts
const noDeny: Check = {
  name: 'no-deny',
  create({ report }) {
    return {
      Action(node) {
        if (node.name === 'deny') report('unknownAction', node, { name: node.name });
      },
      condition(condition) { /* звено цепочки с готовым конвейером */ },
      rule(rule) { /* правило целиком */ },
    };
  },
};
```

Проверка называет код и место в дереве. Уровень, тема и текст берутся из `lint/codes.ts`,
строка и столбец считаются движком. Текст в словаре — английский и запасной: у редактора
свои переводы, по ключу `diag.<код>` в `src/i18n/translations.ts` (см. «Редактор на этом модуле»).

### Настройки: что проверять, а что нет

Второй аргумент `lint`, `lintTree` и `lintWorkspace`. Все поля необязательны.

| Поле | Что делает |
| --- | --- |
| `engine: 'coraza'` | для какого движка написаны правила; без него о различиях движков линтер молчит |
| `only: ['caseNeverMatches']` | проверять только названные коды, остальное выключено |
| `codes: { missingId: 'warning', phasePartial: 'off' }` | по коду: выключить или дать другой уровень |
| `topics: { style: 'off' }` | то же сразу для всей темы: `structure`, `logic`, `coverage`, `environment`, `style`; код, названный в `codes`, сильнее темы |
| `minSeverity: 'warning'` | не выдавать ничего ниже этого уровня |
| `rules: { 921160: ['caseNeverMatches'], 981063: 'off' }` | снять замечания с правила по его номеру — для чужих наборов, которые править нельзя; цепочка считается одним правилом |
| `comments: false` | не слушать пометки в комментариях файла |
| `checks: [...]` | свой набор проверок вместо стандартного |
| `files: ['sql-errors.data']` или `(path, from) => boolean` | какие файлы данных существуют; без настройки `@pmFromFile` и `@ipMatchFromFile` не проверяются — о диске линтер ничего не знает |

Пометки в самом файле — для своих правил, когда находка известна и принята:

```apache
# seclang-ignore: caseNeverMatches
SecRule REQUEST_METHOD "@streq GET" "id:1004,phase:1,pass,t:lowercase"

# seclang-ignore
SecRule ...                              # всё, что линтер сказал бы об этом правиле

# seclang-ignore-file: phasePartial      # на весь файл, где бы ни стояла
```

Пометка относится к ближайшему правилу ниже — целиком, вместе со звеньями цепочки; между
ней и правилом может стоять комментарий-описание.

Пометки проверяются и сами: опечатка в коде (`unknownIgnoreCode`) и пометка, которой нечего
снимать (`unusedIgnore`). Второе — только при полной проверке: если часть замечаний
выключена настройками, судить о лишних пометках нельзя.

Выключенное по коду, теме или уровню отсекается до проверки, а снятое по месту — после:
первому не нужно знать, куда замечание попало бы, второму нужно.

Сейчас 177 кодов в семи темах: форма записи (`structure`, 63), логика (`logic`, 40),
окружение (`environment`, 32), стиль (`style`, 14), охват (`coverage`, 14), журнал (`logging`,
8), скорость (`performance`, 6). Полный список с уровнями — `scripts/seclang.mjs --list-codes`.

Проверки разложены по файлам `lint/checks/` так же, как вопросы к правилу:

| Файл | О чём |
| --- | --- |
| `structure.ts` | форма записи: кавычки, переносы, имена, число аргументов, цепочка |
| `targets.ts` | области проверки: параметры, вычитания, повторы |
| `flow.ts` | тип значения по конвейеру и годится ли к нему оператор |
| `regex.ts` | шаблоны: собирается ли, не подходит ли ко всему |
| `actions.ts` | значения действий, повторы и конфликты, `SecDefaultAction`, реакция и журнал |
| `operands.ts` | макросы, аргументы операторов, противоречия в цепочке, повторы правил |
| `symbols.ts` | метки, переменные, коллекции |
| `captures.ts` | захват: кто заполняет `TX.0`…`TX.9`, кто читает и успевает ли одно к другому |
| `characters.ts` | метка порядка байтов, неразрывный пробел, типографские кавычки, невидимые символы |
| `security.ts` | правило верно, но защищает не так: снимает защиту по тому, что пишет клиент, пишет секрет в журнал, не читает ошибку разбора тела |
| `exclusions.ts` | исключения: дотягиваются ли они до своих правил |
| `environment.ts` | настройки набора, из-за которых правило не работает; значения директив |
| `engine.ts` | чего нет в выбранном движке |

Замечание, которое было бы следствием другого, не выдаётся. В утверждении с незакрытой
кавычкой остаётся одно — о ней: аргументы там разрезаны не так, как хотел автор. То же с
посторонним символом — неразрывным пробелом или типографской кавычкой из скопированного
текста: вместо лавины о его обломках остаётся одно замечание о нём самом. Строка,
у которой после переноса `\` стоит пробел, читается так, как автор задумал, — одним
правилом, — а об ошибке сказано один раз, а не десятью замечаниями о двух обломках.

### Исправления

Часть замечаний линтер умеет починить сам. Исправление выводится из замечания и дерева
(`lint/fixes.ts`), а не записывается проверкой:

```ts
const tree = parse(source);
const fixes = fixesFor(tree, lint(source));     // только те, что чинятся механически
const { source: fixed, skipped } = applyFixes(source, fixes);
```

Чинится то, что можно переписать, не меняя смысла правила: повтор действия,
преобразования или области, пробел после переноса, двоеточие в макросе, пробел перед
оператором, потерянная запятая, `@rx ^слово$` → `@streq слово`. Где нужен выбор — какую из
двух реакций оставить, куда перенести `t:none`, — исправления нет.

Две правки могут задеть одно место (два повтора подряд делят запятую). Вторая тогда
откладывается (`skipped`): после повторной проверки её замечание появится снова, уже с
верными границами. Повторять до конца — дело вызывающего.

### Командная строка

```bash
npm run seclang -- rules/                        # папка: *.conf, по именам
npm run seclang -- modsecurity.conf              # файл и всё, что он подключает через Include
npm run seclang -- --engine coraza rules/        # глазами другого движка
npm run seclang -- --fix rules/                  # применить исправления
npm run seclang -- --format json rules/ > report.json
```

`scripts/seclang.mjs` запускается без сборки: Node 22.15+ исполняет модуль как есть.
Сверх самого линтера он делает то, для чего нужен диск: читает папки, идёт по `Include` и
`IncludeOptional`, проверяет, что файлы данных существуют. Код возврата — 1, если есть
ошибки; предупреждения и советы его не меняют. Остальные ключи — `--help`.

Порядок загрузки при `Include` приближённый: подключённые файлы встают сразу за
подключившим, а не в ту его строку, где стоит директива. Относительный путь в `Include`
считается от папки файла, как у третьей версии и Coraza; Apache со второй версией считает
от ServerRoot — его можно назвать ключом `--server-root`.

Настройки проекта лежат в `seclang.config.json` в текущей папке или выше по дереву, чтобы
не называть движок при каждом запуске:

```json
{
  "engine": "modsecurity3",
  "minSeverity": "warning",
  "codes": { "noNormalisation": "off" },
  "topics": { "style": "off" },
  "serverRoot": "/etc/httpd"
}
```

Ключи те же, что у командной строки (`engine`, `minSeverity`, `only`, `off`, `include`,
`files`, `comments`, `serverRoot`), плюс уровни по коду и теме — как настройка `codes` и
`topics` у `lint`. Ключ командной строки сильнее файла; `--config` называет файл явно,
`--no-config` обходится без него. Опечатка в файле — ошибка запуска: проверить молча не
тем движком хуже, чем не проверить.

## Тесты

Проверяется модуль четырьмя способами, и каждый ловит своё:

- **модульные тесты** (`parser.test.ts`, `analyze.test.ts`, `lint/lint.test.ts`,
  `lint/checks.test.ts`, `lint/refusal.test.ts`, `lint/fixes.test.ts`) — отдельные свойства
  на коротких примерах.
  В `checks.test.ts` больше всего строк вида «а здесь проверка молчит»: почти каждая —
  бывшее ложное срабатывание;
- **размеченные правила** (`cases/*.conf`, `cases.test.ts`) — тест здесь сами файлы правил.
  `clean.conf` — правила без замечаний в разных манерах записи. В остальных у каждого блока
  пометка `# expect:` с кодами, которые линтер обязан выдать: `findings.conf` (форма,
  конвейер, шаблоны, указатели), `reactions.conf` (действия и аргументы), `captures.conf`
  (захват; порядок блоков в нём значим, как порядок правил в наборе), `security.conf`
  (правила, которые защищают не так, как кажется), `exclusions.conf`,
  `environment.conf`, `files.conf`, `coraza.conf` и `modsecurity3.conf` — глазами одного
  движка (строка `# options:` в начале файла задаёт настройки), папка `workspace/` — набор
  из нескольких файлов. Каждый из 177 кодов показан хотя бы раз — за этим следит тест, так
  что новая проверка без примера не пройдёт. `equivalent.conf` — одно и то же, записанное
  по-разному: разбор обязан совпасть. Добавить случай — значит дописать блок в `.conf`;
- **корпус** (`corpus/`, `corpus.test.ts`) — три поколения OWASP CRS и рекомендованные
  конфигурации ModSecurity и Coraza, около 1,8 МБ. Дерево сверяется с исходником, счёт
  утверждений и номеров правил — с подсчётом прямо по тексту, а замечания линтера — с
  поимённым списком известных находок. Подробности и история того,
  что корпус уже нашёл, — в `corpus/README.md`;
- **стенд** (`stand.test.ts`, `stand/`) — линтер против настоящих движков; о нём отдельный
  раздел ниже;
- **масштаб и независимость** (`scale.test.ts`, `independence.test.ts`);
- **командная строка** (`cli.test.ts`) — скрипт запускается отдельным процессом на временной
  папке: `Include`, файлы данных, `--fix`, код возврата.

## Скорость

Один проход по исходной строке, без промежуточных копий; время линейно от длины текста
(`scale.test.ts` держит это и на вырожденном вводе). На ~1 МБ конфигурации (22 тыс. строк,
3300 правил) под jest: разбор ≈ 12 мс, анализ ≈ 2 мс, проверки ≈ 5 мс.

## Редактор на этом модуле

Редактор правил (`src/modsec`, `src/context`, `src/components`) своего парсера и своих
проверок не имеет: и то и другое — этот модуль. Сам модуль о редакторе по-прежнему ничего
не знает; ниже — что редактор у него берёт и что из этого следует для того, кто модуль правит.

| Что нужно редактору | Чем отвечает модуль | Где это в редакторе |
| --- | --- | --- |
| Разобрать файл | `parse` — дерево; редактор раскладывает его в документ по утверждениям, с пустыми строками и текстом каждой | `src/modsec/parser.ts` |
| Разобрать часть правила, набранную в форме | `parseVariableList`, `parseOperator`, `parseActionList`, `parseArguments` | там же |
| Замечания о наборе файлов | `createWorkspace`: `set` на каждый файл, `lint()` на набор | `src/modsec/inspect.ts`, `src/context/useInspection.ts` |
| Можно ли показать файл в конструкторе | `lintTree(tree, { only, comments: false })` по короткому списку кодов о форме записи | `src/modsec/compile.ts`, список — `BLOCKING_CODES` в `src/modsec/diagnostics.ts` |
| Кнопка «исправить» | `fixFor`, `applyFixes` | `src/modsec/fixes.ts` |

`parseArguments` появилась ради редактора, но о нём не знает: это аргументы одной директивы —
слова со снятыми кавычками и переносами, как их режет разбор файла. У разобранных директив
(`SecDefaultAction`, семь исключений) дерево хранит уже прочитанные части, а формам редактора
нужны именно слова; резать строку своим кодом значило бы завести второе правило о том, где
кончается аргумент.

От себя редактор добавляет только то, чего модулю знать неоткуда: место замечания в
конструкторе (блок, звено цепочки, часть правила — выводится из узла, на который замечание
поставлено), имя файла у повтора номера через файлы и оговорку «для этого действия в форме нет
поля».

**Закрыта ли визуальная вкладка, решает не уровень замечания.** Уровень отвечает на вопрос
«загрузит ли запись движок», и ответ зависит от движка. Конструктору важно другое: может ли он
показать запись формой и собрать её обратно. Шаблон, который не собирается, не загрузит ни один
движок, а форме он не мешает — поле краснеет, и чинят его там же, где набрали. Поэтому список
закрывающих кодов у редактора свой и короткий, и смена уровня в `codes.ts` на него не влияет.

### Что нужно сделать в редакторе, когда меняется модуль

- **Новый код** — дописать `diag.<код>` в оба словаря `src/i18n/translations.ts`. Ключ перевода
  типизирован, и без записи не пройдёт сборка редактора (`npx tsc -b`): забытый перевод должен
  быть ошибкой сборки, а не сырым ключом в интерфейсе.
- **Новая фраза в подстановке.** Большинство подстановок — значения из файла, но некоторые
  проверки отдают готовые английские слова: `expected: 'a positive whole number'`,
  `actual: 'raw bytes'`. В русском тексте они остались бы вкраплениями, поэтому у редактора есть
  словарь таких фраз (`CORE_PHRASES` там же), а тест `src/i18n/translations.test.ts` прогоняет
  размеченные правила из `cases/` и называет фразу, которой в словаре нет.
- **Новое исправление** — подпись кнопки: таблица `TEXT_FIX_KINDS` в `src/modsec/fixes.ts`
  (тест сверяет её с `FIXABLE`).

### Что изменилось в редакторе с переходом

Прежний парсер редактора читал запись удобнее, чем движок; этот читает так же, как движок.
Перед переходом оба разбора были сверены на всём корпусе, размеченных правилах и учебных
примерах редактора: из 16 863 утверждений разошлись 117, и все расхождения — из этого списка.

- Перенос `\` внутри кавычек исчезает бесследно, а не превращается в пробел.
- Пробел в конце аргумента оператора остаётся его частью. В CRS так записаны шаблоны на
  веб-шеллы (`<title>lostDC - `): прежний разбор пробел срезал, и правка такого правила в
  конструкторе молча расширила бы шаблон.
- Пробел перед `@` делает запись шаблоном (`" @rx a"` движок читает не как оператор).
- Строка с пробелом после переноса читается одним правилом, как задумал автор, — с замечанием
  `continuationSpace`; прежний разбор видел два обломка.
- Имена директив, действий, операторов и переменных сравниваются без учёта регистра. Редактор
  получает их в принятом написании: `t:compressWhiteSpace`, сто раз записанное так в CRS 2, —
  то же преобразование, что `t:compressWhitespace`, и форма обязана его узнать.
- `SecRuleScript` для проверок — правило со своим списком действий; в конструкторе он остался
  строкой.
- Число — это ещё и текст: `RESPONSE_STATUS "@rx ^5\d\d$"` замечанием не считается.
- `ARGS` в первой фазе — не ошибка фазы, а совет (`phasePartial`): параметры строки запроса
  там уже есть.
- Каталог шире: все переменные и директивы ModSecurity 2 и 3 и то, что добавляет Coraza, а не
  только те, для которых в редакторе есть форма.

Проверки прежнего редактора перенесены сюда все, под теми же кодами и с теми же именами
подстановок, — поэтому его переводы подошли как есть. Три нарочно осторожнее прежних:

- `duplicateRule` — нужны не только те же условия, но и та же фаза и те же действия: на CRS,
  где каждый файл начинается одним и тем же условием на уровень паранойи, замечаний иначе
  были бы сотни;
- `noNormalisation` — не выдаётся правилам, которые проверку ослабляют (`ctl`, `skipAfter`,
  `allow`): исключение, не узнавшее путь в чужом регистре, просто не сработает;
- `exclusionNoMatch` — только когда видно, что нужная часть набора загружена.

Таблицы самого редактора (`src/modsec/semantics.ts`: подписи, подсказки, порядок полей) остались
у него. Чтобы они не разошлись с каталогом в написании имён и в устройстве переменных и
операторов, есть тест `src/modsec/semantics.seclang.test.ts`.

## Откуда сведения о движках

Всё, что линтер утверждает о поведении движка, взято из исходников, а не из памяти:

- ModSecurity 2 — `apache2/re.c` (разбор списков, цепочки, `skipAfter`), `re_actions.c`
  (значения действий, `ctl`, макросы), `re_operators.c`, `apache2_config.c`
  (`SecDefaultAction`, директивы-исключения), `msc_tree.c` (списки адресов);
- ModSecurity 3 — `src/parser/seclang-scanner.ll` и `seclang-parser.yy`, `src/rule_with_actions.cc`
  (сравнение тегов), `src/utils/msc_tree.cc`;
- Coraza 3.8.1 — `internal/seclang`, `internal/corazawaf`, реестры операторов, действий и
  преобразований.

Прочитанное сверено с самими движками — об этом следующий раздел.

## Стенд: линтер против настоящих движков

Исходники можно прочитать неверно, и несколько раз так и вышло. Поэтому те же правила
отдаются трём настоящим движкам, а их ответ записывается и сверяется с линтером на каждом
прогоне тестов.

```bash
node scripts/engines/run.mjs all --write     # нужен Docker; минут пять
```

Движки — ModSecurity 2.9.15 под Apache, libmodsecurity 3.0.17 под nginx (образы
`owasp/modsecurity-crs`) и Coraza 3.8.1, для которой в контейнере `golang` собирается
маленький загрузчик (`scripts/engines/coraza/main.go`). Стенд делает три вещи:

- **имена** — каждое имя каталога в самом малом правиле: грузит движок или нет. Сверяется
  с таблицами `engines.ts`;
- **загрузка** — каждый блок из `cases/*.conf` и каждая проба из `stand/probes.conf`
  отдельным файлом: 488 блоков на три движка. Что движок не загрузил, то линтер с этим
  движком обязан назвать ошибкой, и наоборот;
- **поведение** — 155 сценариев с настоящим запросом (`scripts/engines/scenarios.json`):
  правила, запрос и чем он кончился в каждом движке. Так проверено то, чего при загрузке не
  видно: раскрывается ли макрос, снимает ли исключение правило, в каком порядке всё
  исполняется.

Вердикты лежат в `stand/verdicts.json`, и `stand.test.ts` сверяет с ними линтер уже без
Docker. Вердикт о блоке хранится по отпечатку его текста: поправили блок — старый вердикт
к нему больше не относится, и тест скажет, что стенд пора перезапустить.

Расхождения, которые остались, перечислены в `stand.test.ts` поимённо и с причиной. Их два
рода. Движок блок не загрузил, а линтер не возражал, — причина всегда вне текста правила:
файла нет на стенде, блок вырван из набора. Линтер называет запись ошибкой, а движок её
грузит — потому что ошибка у линтера это ещё и «загрузится так, что правило заведомо не то,
что написано»: цепочка без продолжения, правило без номера, незнакомый оператор, который
третья версия молча читает как шаблон.

Спросить движки о своих правилах:

```bash
node scripts/engines/run.mjs probe путь/к/папке   # каждый *.conf — в три движка
```

Чего стенд не проверяет: ModSecurity 2 вне Apache (у подключений к nginx и IIS свой разбор
строки директивы, и слэши там могут сворачиваться иначе), другие версии тех же движков,
поведение под нагрузкой.

## Чего линтер не видит

Список честный: всё перечисленное — известные пробелы, а не «мелочи».

**Язык и разбор**

- Контекст Apache: `<VirtualHost>`, `<Location>`, `<IfModule>`. Правила внутри них
  считаются лежащими в общем наборе; что номер может повторяться в разных контекстах, а
  правило действовать только в одном, линтер не знает.
- Порядок при `Include` посреди файла приближённый (см. «Командная строка»).
- Слэши считаются по правилам ModSecurity 2 под Apache: он сворачивает `\\` в `\`
  раньше, чем строку увидит движок. Подключения второй версии к nginx и IIS читают
  конфигурацию своим кодом и на стенде не проверялись.
- `ctl:ruleRemoveById` в третьей версии не снимает безусловные `SecAction` — только правила
  с условием. Стенд это показал, замечания об этом нет.
- `@pmFromFile a.data b.data`: Coraza читает аргумент как одно имя файла. Замечания нет.
- `exec` в третьей версии принимает только сценарии на Lua. Замечания нет.
- `capture` в `SecDefaultAction` вторая версия и Coraza исполняют, третья — нет. Линтер
  считает его захватом для всех и о разнице молчит.
- После захвата с меньшим числом групп, чем у прошлого, вторая версия стирает старшие
  группы, а третья и Coraza оставляют в них прежнее. Замечания нет.
- `^` и `$` в третьей версии и Coraza — ещё и границы строк. Линтер говорит об этом там,
  где строка открывает дорогу: у отрицания (`!@rx ^\d+$`) и в правиле, которое снимает
  защиту (`allow`, `ctl:ruleRemove…`, `skipAfter`). У правила обнаружения лишняя строка
  только находит больше, и замечания нет. Какие значения однострочны, линтер знает по
  переменной (`OneLine`); значения `TX` и имена файлов из тела ему неизвестны.
- `^$` после завершающего перевода строки (`x\n`) совпадает в Coraza и не совпадает в
  PCRE обеих версий ModSecurity. Замечания нет.
- Раскодирование пути и `REQUEST_URI` (таблица в «Движках») линтер учитывает для якорей и
  `@validateUrlEncoding`, а в остальном о разнице молчит. Правило первой фазы на
  `REQUEST_FILENAME` без `t:urlDecodeUni` во второй версии видит путь как прислали, и
  `/%61dmin` мимо `@beginsWith /admin` пройдёт — в третьей версии и Coraza нет. Шаблон с
  `%2e` на `REQUEST_URI` в третьей версии не найдёт ничего, а `t:urlDecodeUni` на нём
  раскодирует там второй раз. Замечаний об этом нет.
- Сборки с другим поведением якорей: третья версия с `--enable-regex-dollar-endonly`,
  Coraza с меткой `coraza.rule.no_regex_multiline`. Линтер считает, что сборка обычная.

**Смысл**

- Недостижимый код: правила между безусловным `skipAfter` и его меткой, правила после
  безусловного `deny`.
- `block` без `SecDefaultAction` с блокирующей реакцией — то есть `block`, который на деле
  `pass`. В CRS это задумано (режим подсчёта аномалий), отличить задумку от ошибки нечем.
- `multiMatch` без единого преобразования; `(?i)` в шаблоне после `t:lowercase`; двойное
  раскодирование (`t:urlDecode,t:urlDecodeUni`).
- `%{TX.12}`: групп больше десяти движок не хранит. `@ge 5.5`: дробная часть отбрасывается.
- `MATCHED_VAR` как область проверки в правиле без цепочки, где совпадать ещё нечему.
- Повтор правила ищется в пределах файла, а не набора.
- Переменные, которые кладут сценарии на Lua (`SecRuleScript`, `exec`): в файлах правил
  записи нет, и замечание «никто не выставляет» для них верно только буквально.

**Настройки**

- Предел `SecPcreMatchLimit`. Правило на `TX:MSC_PCRE_LIMITS_EXCEEDED` в рекомендованных
  конфигурациях стоит не зря, но на стенде шаблон, упёршийся в предел, ни в одном движке
  не открылся (сценарий `pcre-limit-fail-open`): оптимизации PCRE успевают раньше. Пока
  такой шаблон не найден, проверки нет.
- `REQUEST_BODY` у запроса JSON без обработчика тела заполняет одна третья версия
  (сценарий `json-request-body-variable`). Замечания нет: тип тела известен только на
  запросе.
- Как вторая версия обходится с испорченным XML, стенд не выяснил: на этом запросе она не
  доходит даже до безусловного правила второй фазы (`diag-phase2-runs`). Замечание
  `bodyErrorUnchecked` опирается на Coraza и рекомендованные конфигурации.
- Противоречия между директивами: `SecRuleEngine` дважды с разными значениями,
  `SecAuditLogType Concurrent` без `SecAuditLogStorageDir`, пределы тела запроса, которые
  не согласуются между собой.
- Существование файлов проверяется только для `@pmFromFile` и `@ipMatchFromFile`; сценарии
  (`exec`, `@inspectFile`, `SecRuleScript`), `SecUnicodeMapFile`, база GeoIP — нет.

**Движки**

- Версии внутри одного движка: что появилось в ModSecurity 2.9 или 3.0.10, не различается.
- Поведение, а не запись: одинаково названное действие, работающее чуть иначе
  (`ctl` в Coraza, порядок действий в цепочке у третьей версии). Известное перечислено в
  таблице раздела «Движки»; всё остальное — нет.
- ReDoS оценивается по одной примете (вложенный квантор). Это подсказка, а не анализ.
